# 0.2.0 干净主站验收清单

## 状态与安全前提

这是**待用户执行的验收计划**，不是通过报告。仓库自动化测试不替代干净 FBA 主站安装、前端权限、真实 Nginx 下载或 Windows 客户端验证。不预填实测兼容版本。

- 每个组合使用独立、可销毁的专用测试数据库和 Redis 命名空间/实例，不接入生产或既有业务库。
- `FBA_INTEGRATION=1` 只用于上述环境。不要在现有库执行 `fba init`，它会 `drop_all`；若从零准备宿主，请先确认目标是可销毁的测试库。
- 卸载、destroy 和故障模拟会破坏数据，先备份数据库、产物和配置并验证恢复路径。
- 锁定宿主 SHA、后端插件 SHA、前端插件 SHA；服务器使用宿主固定的子模块指针，不用 `--remote`。

## A. 自动化检查（独立证据）

从宿主根目录执行并保存当前 SHA 及完整输出：

```bash
pytest backend/plugin/app_update/tests/ -q
# 仅专用集成环境
FBA_INTEGRATION=1 pytest backend/plugin/app_update/tests/ -q
```

记录通过、失败、跳过数及跳过原因。版本、manifest、产物存储、签名信息、发布/feed、配置、生成器的自动化检查只证明各自测试覆盖的行为；mock、SQLite 或静态 SQL 解析不算真实 MySQL/PostgreSQL 四组合验收。

## B. 每个数据库/主键组合均执行

### 1. 新安装及 seed

- [ ] 主站无本插件表/菜单，宿主数据库与主键配置确认为当前组合。
- [ ] 选择 README 的 CLI Git 或 ZIP 安装；ZIP 为 `app_update.zip`、唯一顶层为 `app_update/`。记录 CLI 先 ORM 建表再通过官方解析器执行对应 init 的日志。
- [ ] 另外在隔离副本验证 submodule/手工路径：先执行匹配 `schema[_snowflake].sql`，再执行对应 init；不是仅复制目录后启动。
- [ ] 安装后应用、渠道、版本、产物表存在，主键模式正确；菜单/按钮权限、默认 `demo`、`stable`、`beta` 可见。自增模式不被固定大 ID 抬高计数器；雪花模式前端保留主键／外键字符串，新增应用、渠道、版本及关联筛选不丢精度。
- [ ] 再执行同一 init，无重复菜单/seed，无错误。修改 demo 名称、渠道状态/其他业务字段后再次 init，确认用户数据不被覆盖、已停用渠道不被恢复。
- [ ] 重启后端并构建配套 UI 0.2.0，无未知配置或模型加载错误。

### 2. 配置和角色权限

- [ ] 六字段均从插件独立配置读取；验证环境变量覆盖 `.env`、`.env` 覆盖 TOML，重启后生效，不修改宿主 conf。
- [ ] 专用环境验证非法整数、超出 16 MiB 的 manifest/chunk、非法 URL 会启动失败；恢复有效值后能启动。
- [ ] 非超级管理员默认不能越权操作；为测试角色分配页面及所需按钮后可见、可操作。
- [ ] 分别撤销上传/发布/暂停权限，管理 API 拒绝对应未授权操作，不能只依据按钮隐藏判定安全。

### 3. 两版本发布、暂停与回退

- [ ] 用测试应用 `myapp` / `stable` 构建 `1.2.3`、`1.2.4` 的 Windows x64 NSIS 包及对应 blockmap；实际文件名符合 `Myapp-x.y.z-win-x64.exe(.blockmap)`。
- [ ] 使用 `scripts/generate_manifest.py --application-key ... --version ... --installer ... --blockmap ... --output ...` 生成 manifest，不提供签名文件时状态为 `unknown`。
- [ ] 草稿上传三产物并发布 1.2.3，feed 的版本、大小和 sha512 与包一致。
- [ ] 发布 1.2.4，feed 切换至新版本，重启后结果保持；已发布版本无法重新上传、同名文件不被覆盖。
- [ ] 暂停历史非当前版本时，当前 feed 保持不变。暂停当前 1.2.4 时，若 1.2.3 仍为 published 则回指它；暂停最后一个可用版本时 feed 404。记录客户端策略，不能将 feed 回退视为客户端必然降级。
- [ ] 应用/渠道停用时 feed 404；恢复后按实际状态重新验证。
- [ ] 其他应用、其他渠道不受上述切换影响。

### 4. 下载与公开边界

按 `examples/nginx/README.md` 在 server 级 include 并替换域名、upstream、共享目录，先进行 Nginx 配置检查。用真实入口而非仅后端测试客户端：

```bash
curl -i https://downloads.example.com/updates/myapp/stable/latest.yml
curl -I https://downloads.example.com/updates/myapp/stable/Myapp-1.2.3-win-x64.exe
curl -i -H 'Range: bytes=0-1023' \
  https://downloads.example.com/updates/myapp/stable/Myapp-1.2.3-win-x64.exe -o range-response.bin
```

以上域名需替换，输出文件只用于测试，检查响应头和实际数据长度。

- [ ] 动态 feed 经后端返回，不被静态旧 YAML 覆盖；安装包和 blockmap 可下载，摘要一致。
- [ ] Range 返回 206，`Content-Range` 和字节数正确，完整包可由 Windows 客户端下载/安装更新；记录真实客户端版本及结果。
- [ ] manifest、`.staging`、目录、任意非白名单文件及其他 `/updates/` 路径均 404；后端宿主静态路由也不意外暴露敏感文件。
- [ ] 暂停/停用后 feed 404 或回退，但旧包 URL/缓存仍可能可用；确认运维理解撤包需另行处理源站/CDN，不能误记为安全缺陷已自动封禁。

### 5. 无签名信息和历史兼容

- [ ] 缺少可选签名字段的合法 manifest 不阻断正常发布；状态 `unknown` 不被自动提升为 `valid`。
- [ ] 列表/详情显示空或部分签名信息，不将声明渲染为“服务器验签通过”。
- [ ] 专用数据副本模拟缺失/损坏 manifest，列表/详情返回 `signature_info: null` 而非整体失败，不泄露服务器绝对路径，不改变 `signature_status`。

### 6. 卸载与恢复（破坏性）

- [ ] 已备份并确认该测试环境可销毁，记录恢复演练结果。
- [ ] CLI 路径执行 `fba remove app_update`，确认对应 destroy 经宿主卸载解析路径成功执行；代码 ZIP 备份不当作数据备份。
- [ ] 手工路径在隔离副本用原生客户端执行匹配 destroy，移除插件/submodule、前端、配置及代理映射，重启/构建。
- [ ] 在插件菜单下放置临时自定义子菜单后尝试卸载，应在删除任何数据前拒绝；移走自定义节点后再验证正常卸载。
- [ ] 插件表、菜单、相关角色授权已清理且宿主其他业务表未被删除；清理产物后旧下载入口不可用，另行核查 CDN 缓存。
- [ ] 重新安装及恢复备份演练可复现，记录失败和人工步骤，不用 `fba init` 修复业务库。

## C. 既有 0.1 升级副本

- [ ] 从脱敏备份建立独立升级副本，记录升级前表结构、版本、签名状态及产物摘要。
- [ ] 更新后端和 UI 至 0.2.0、同步配置和 Nginx，重启/重建；**不执行结构迁移、不回填签名字段、不销毁重建数据库**。
- [ ] 历史无签名信息记录正常显示，原有数据和摘要不变，发布/feed 正常；如重复 seed，已有数据不被覆盖。

## 放行条件

四行矩阵及升级副本均需真实证据；不适用、失败、跳过项由维护者明确评估后决定支持范围。当前公开副本由已验证源码创建独立初始提交，不携带原开发历史，维护者为 SoulEater。后续发布仍应审查新增提交、附件、凭据和许可声明；本清单本身不授权 Git 历史改写、强推或生产部署。
